# diskOS Disco 2.5.0: performance, memory and binary-size review

Baseline: public GitHub `main`, commit `f4c7af680553a70b52a633eb0fd7a6b38c46a60a`, verified against GitHub during this review. This is the fixed 2.5.0 with the right-end-full battery arc, QS settings/EQ behavior, artwork/blur changes, and prior corrections. No older release checkout is used for the delivered patch.

Scope: retain every feature; preserve all animation timings and appearance except the explicitly authorized Squash volume entrance/exit. Disco and Null volume code is unchanged. Review findings below are not claims that every issue causes the reported device hangs. Source inspection and native LVGL tests cannot establish the cause of audio dropouts without device evidence.

Preserve transition overlap. | Confirmed symbols; proposed. Do not simply union buffers: multiple representations coexist during transitions. |
| S1 | High / best size opportunity | Roulette's raw wheel image is 518,400 bytes in read-only executable data. | Store it losslessly compressed and expand once into the themed buffer Roulette already allocates. ## What was implemented: Squash volume only

- Same 0–120 range, arc hit area, number, logo/outside dismissal, and final settled drawing.
- Same maximum one volume command per 120 ms during movement; pending final value is sent on release or press-lost.
- No 350 ms quiet-period/echo-reconciliation machinery. Incoming reports update the displayed level as soon as no drag or unsent adjustment owns it. Like Disco/Null, this can expose a delayed player report; queued commands are not acknowledgements of physical audio level.
- A failed send gets at most four attempts for that target. The retry timer runs only after failure, stays alive after dismissal when needed, pauses after success/exhaustion, and does not fight an active drag. Exhaustion still reports an error.
- The ordinary timer is back to an inactivity timeout, not 20 checks per second. Normal visible operation has no retry polling.
- Volume moves 12 px instead of 64 px on entry. Entrance/exit are 96/70 ms, matching Null's durations; no new fade layer or scaling. With animations off, show/hide is immediate.
- Other animations, themes, QS behavior and previous fixes are unchanged.

This is a small responsiveness change, not a claimed cure for player crashes or an OOM fix.

## File size: measured opportunities, not promised final savings

The current public main payload is **6,185,624 bytes** (about 5.90 MiB), already statically linked, stripped, built with `-Os`, function/data sections and linker garbage collection. Recommending those same flags would not produce new savings.

The Roulette image contains 129,600 exact 32-bit pixels:

| Representation experiment | Bytes | Raw-data reduction |
|---|---:|---:|
| Existing raw pixels | 518,400 | — |
| Simple lossless 6-byte run-length records | 146,070 | 372,330 |
| Deflate level 9 | 45,858 | 472,542 |

The run-length experiment round-trips every pixel exactly. These are **data-only measurements**: final executable savings would subtract decoder/metadata changes. Compression must happen once when opening Roulette, never on every animation frame. This is the strongest feature-preserving size candidate identified here.

Font compression and whole-program optimization are secondary experiments. Neither has an established safe device saving from this review. In particular, this project contains an explicitly `-O0` float-heavy artwork region because optimized MIPS code previously crashed; global optimization experiments must respect that boundary. Do not switch to legacy-NaN/FP32 toolchains or pack the executable merely to make the download smaller.

### Volume build result

The new stripped device test binary is **6,185,528 bytes**, **96 bytes smaller** than the public-main payload. Its linked text/read-only total falls by 96 bytes and `.bss` by 16 bytes; initialized data is unchanged. This is a small control simplification, not the large size optimization proposed above. None of the unimplemented asset/font/cache recommendations is counted as a delivered saving.

The device link and theme gate passed. ELF inspection confirms static little-endian MIPS32r2, o32, hard-float FP64, NaN2008. GCC 11.2.0 and musl 1.2.6 were rebuilt from the repository-pinned sources; kernel headers came from the matching upstream `v4.19.88-2` commit `22bba0124dfe2728ef5b4555baa1ae0960492665`. Unchanged MIPS objects from the verified public-main build were reused; changed production source was recompiled and the executable relinked. This was not a physical-device execution test.

## Memory observations and interpretation

The user's measured UI RSS was 36,420 KiB, peak RSS 42,456 KiB, with 21,056 KiB system MemAvailable and no swap. Those snapshots do not show an ongoing leak or establish memory exhaustion. They do not exclude transient decoding peaks, another process growing, storage delays or CPU starvation.

The decoder already has a bounded allocation budget and an 8 MiB reserve based on a MemAvailable snapshot. That is useful protection, not a guarantee against OOM: other threads/processes allocate concurrently, and the budget does not represent every allocation in the process. Existing decoding is serialized, but an in-process decode is not interrupted mid-call by a skip: stale results are rejected afterwards. Making long work more cooperative is an additional candidate, not a reason to remove format support or quality.

Large individual symbols in the matching unstripped main build include 397,488-byte RGB artwork, two 529,984-byte 364px buffers, and several 518,400-byte backdrop/frame buffers. They are not all interchangeable. Zero-initialized `.bss` costs virtual/runtime storage, not the corresponding number of executable-file bytes; it must not be counted as a file-size saving.

## Library row investigation

The native fixture jumped from Music to a specific track, then performed a real pointer scroll. Its filled background remained fully opaque. This proves that the explicit Library location marker persists across scrolling. It does not prove arbitrary rows receive this marker without a prior navigation action.

Library rows are deleted/recreated by virtualization rather than blindly rebound, so there is no evidence here of recycled rows inheriting a checked state. Ordinary touch focus also affects which long label scrolls, but the filled location marker is applied separately by `focus_mark()`. The proposed fix is to make the marker's lifetime explicit on manual browsing, not indiscriminately clear checked/focused states across all widgets.

A queue-scroll concern raised during inspection was **not reproduced** in the isolated long-running animation check and is excluded from the confirmed bug list. The callback's wording and mode deserve cleanup, but no sustained CPU defect is claimed from that test.

## Validation and limits

- Native LVGL volume regression covers drag throttling, final release/press-lost, failed-send recovery, four-attempt exhaustion, retries after dismissal, no retry traffic during a held drag, immediate new player reports, 0/120 clamps, timeout and dismissal.
- Rapid close/reopen tested for 24 cycles with animations on/off. Disabled animations use no entrance/exit animation.
- Twelve native interaction cases passed: Squash volume in both palettes, Null volume, Squash gesture/hold/refresh behavior, and EQ actions in Disco/Null/Squash.
- Thirty-six settled home/Quick Settings/volume screens compared byte-for-byte against the public-main build across all six active themes and both variants. No pixel differences.
- Theme-role build gate, generated-palette consistency and whitespace checks passed.
- Hardware listening, CPU, SD-latency and long-run RAM measurements remain device work. No physical Disc installation was performed and no release/tag/assets were changed by this review.

## Suggested implementation order after the volume test

1. Pause hidden Album Wall polling; free completed seed snapshots; make the Library marker's lifetime explicit.
2. Add short timing diagnostics for UI-thread database/SD calls and prewarm duty cycle, then reproduce a device slowdown.
3. Apply the lossless Roulette asset change and verify exact pixels and safe allocation/fallback paths.
4. Move Album Wall I/O off-thread and make background artwork more deferential to playback.
5. Evaluate font compression and larger metadata/buffer-lifetime changes only with device measurements.
